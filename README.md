# Elastic M-26-14 Logging Readiness Package (site)

React + Vite static site. `npm install`, `npm run dev` to work locally, `npm run build` to produce `dist/`.
Vercel builds from `main` with the default command; `vercel.json` rewrites every path to `index.html`.

## Build flags

| Variable | Effect |
|---|---|
| `VITE_ENABLEMENT=on` | Mounts the internal field-enablement pages (`/enablement`, `/enablement/sales`, `/enablement/sa`) and turns the header logo into their entry point. Off by default, so the deployed customer build ships no route to them (design call DC-8, LRA change review). Set it for an internal deploy or a local `npm run dev`; never in the Vercel production environment. |

Vite inlines the value at build time; the pages are absent from the bundle's route table, not hidden behind a redirect.

## Capabilities page data

`/capabilities` is built from two files, cross-checked by `scripts/check-catalog.mjs` before every `dev` and `build` (also `npm run check`):

| File | Source |
|---|---|
| `src/data/assetCatalog.json` | Generated by the pack: `python3 tools/gen-asset-catalog.py --out <this repo>/src/data/assetCatalog.json --kibana-env <env file> --host-var PUBSEC_KIBANA_HOST --key-var PUBSEC_API_KEY`. The `--kibana-env` arguments resolve the demo cluster's saved-object ids (detection rules are minted at install; the osquery pack too), so links open the right object. The key is read from the env file and never written anywhere. Regenerate after every pack change; the check fails the build if a capability names an asset that no longer ships or a shipped asset no capability describes. |
| `src/data/capabilities.js` | Hand-authored: each capability's text, the asset ids that contribute to it and the dashboard screenshots to show. |
| `public/screenshots/<dashboard id>.png` and `thumbs/<id>.jpg` | Captured from the demo cluster through the Kibana reporting API (`POST /api/reporting/generate/pngV2` with a `DASHBOARD_APP_LOCATOR` job, 1600 x 1200 preserve-layout, 7d for operations views, 30d for posture views, 90d for inventory views), then `sips -Z 640 -s format jpeg` for the thumbnail. All 21 dashboards are captured (2026-09-21, after LRA change-review items R-89 and R-94 were applied live and the R-97 drilldown fixes re-uploaded). Recapture a dashboard whenever its panels change and keep the same file name; the capability's `shots` list references the id. |

## Elastic Hub page

`npm run build:hub` builds `dist-hub/index.html`, one self-contained HTML file for Atrium on the Elastic Hubs. Atrium serves it in a sandbox with an opaque origin, so everything the app loads from `public/` is inlined (screenshots re-encoded as 1600px JPEGs, PDFs linked to this repository on GitHub instead), routing happens in memory, and the build fails if the page is over Atrium's 10 MB limit or loads anything from the network.

`.github/workflows/build-hub-asset.yml` runs on every push to `main`: it builds the page, opens or updates a pull request with it for `hub/` when it changed (main requires a pull request), and publishes it with the `eh` CLI to the Atrium assets on the field hub (`0037f023-05b5-4209-b9f2-3a53a694fcbc`) and the GPS hub (`ebd24c25-e448-473c-9694-2eaf66dde671`). The publish job runs in the `hub-publish` environment and authenticates as the publisher service account through Workload Identity Federation; see the comments in the workflow.
